# BOTW-PC 第五輪報告：GPU 前端重寫（2026-10-15）

## 結論

- **新的「優化 GPU 前端」已實作、整合、驗證並提交。** 用同一個執行檔、交錯各跑 4 次比較：
  - 平均 **+2.17 FPS（95% CI +0.50..+3.84，+2.6%）**
  - GPU 命令執行緒 **−0.77 ms/幀（−8.1%）**
  - 遊戲速度 1.000；CPU 和記憶體沒有變化
- **正確性有實證：**
  - 執行期差分驗證比對了 8.13 億次暫存器寫入，**0 個不一致**
  - 30 FPS 的遊戲軌跡和舊版**完全相同**
- **預設仍是 legacy（舊路徑）：**
  - 你的存檔還在初始台地，龍、馬、戰鬥場景都驗證不到，上線條件沒全部過關
  - 想用的話可以在設定開啟（見 E 節）
- **120 FPS 沒有達成**，這輪也確認了原因：
  - 剩下的 GPU 執行緒時間大多是每次 draw 必須做的工作，Eden 也照樣在做
  - 另外三個「理論上可省」的捷徑都實測沒效果，已撤回

## A. 前端架構

**名詞：**
- **GPU 前端**：模擬器裡把遊戲送出的 Maxwell GPU 命令翻成主機繪圖指令的部分，跑在 GPU 命令執行緒上。
- **暫存器寫入**：每個命令字幾乎都是「把某個值寫進 GPU 的某個設定欄位」。

| 項目 | 內容 |
|---|---|
| 原本的路徑 | 每個命令字都進 `Send()` → `ThreedClass.Write` → 影子暫存器層 → `DeviceState` → 狀態群組追蹤。中間經過 3 層包裝、2 次查表 |
| 新路徑（fast register dispatch） | 3D 命令直接進專用路徑。每個暫存器有 1 個位元組的「種類表」：有回呼的走舊路，其餘一次完成影子 RAM 處理、比較、寫入、標記髒群組 |
| 重寫的部分 | 命令分派、暫存器寫入路徑 |
| 保留的部分 | 狀態群組、draw 流程、buffer／texture 綁定、各種快取、GAL、Vulkan、記憶體追蹤、readback 提早送出、第四輪的 binding memo 和 page table |
| 開關 | `BOTWPC_GPU_FRONTEND=legacy\|optimized`，或 `settings.json` 的 `graphics.gpu_frontend`（`Legacy`／`Optimized`）。每個元件都能單獨關閉，也能做 A/B |
| 參考來源 | Eden（GPL-3.0）只讀演算法，沒有複製任何程式碼；Ryujinx 是 MIT |

**為什麼沒有整個重寫：**
- 實測後，每個命令字只剩約 6.4 ns。
- 其餘約 59% 的時間在每次 draw 的流程：綁定約 37%，加上狀態更新和送進 render 佇列。
- 這些是記憶體模型必須做的事，Eden 也一樣每次 draw 都同步 buffer、重讀 texture handle。
- 第四輪試過兩種多執行緒拆法，都比較慢。
- 換一套新程式只會重做同樣的工作。

## B. 差分正確性

| 驗證項目 | 結果 | 說明 |
|---|---|---|
| Maxwell 暫存器狀態 | **PASS** | 執行期 8.13 億次（最終版）＋前一版 6.98 億次，0 不一致。單元測試：隨機串流、負對照、你的存檔錄下的 800 萬次真實寫入 |
| Macro 副作用 | NOT TESTED（直接比對） | 呼叫的函式、參數、順序都和舊路徑相同，靠遊戲測試涵蓋 |
| Buffer 綁定 | 程式未變更 | 試過的 sync memo 驗證通過後，因為沒效果而撤回 |
| Texture 綁定 | 程式未變更 | — |
| GPU 記憶體副作用 | 程式未變更 | — |
| Syncpoint／fence | 程式未變更 | — |
| Readback 數值 | 程式未變更 | — |
| Draw／compute 輸出 | PARTIAL | 截圖正常；兩種模式無法渲染同一幀，所以沒有逐像素比對 |
| 資源失效 | 程式未變更 | — |
| 完整遊戲回歸 | **PARTIAL** | 30／60／90／120 模式、DLSS 都通過；龍、馬等場景驗證不到 |

**驗證器實際抓到過問題：**
- sync memo 的第一版對 4 KiB 的整塊追蹤 buffer 判斷錯誤，2.32 億次檢查中有 3,564 次不一致。
- 是 log 裡的不一致紀錄抓到的，不是靠看截圖。
- 修正後 0 不一致，但量測沒有效果，所以最後還是撤回。

## C. 效能（W2：你的存檔，1080p，DLSS 關）

測法：同一個執行檔，legacy／optimized 各 4 次交錯，每次都經過有效性檢查。

| 指標 | Legacy | Optimized | 變化（95% CI） |
|---|---|---|---|
| 平均 FPS | 84.06 | 86.23 | **+2.17（+0.50..+3.84）** |
| 中位數 FPS | 85.44 | 87.71 | +2.27（+1.15..+3.39） |
| 1% Low | 59.95 | 59.03 | 不顯著 |
| P95 幀時間 | 13.85 ms | 13.44 ms | 不顯著 |
| P99 幀時間 | 15.46 ms | 15.12 ms | 不顯著 |
| GPU 命令執行緒 | 9.48 ms | 8.72 ms | **−0.77（−1.25..−0.29）** |
| 每個命令字的成本（解碼＋寫入） | 8.7 ns | 6.4 ns | −27% |
| 等 GPU 資料的時間 | 0.436 ms | 0.322 ms | −0.115 |
| Binding commit | 2.66＋1.06 ms | 2.69＋1.07 ms | 沒變（程式未改） |
| Render 執行緒 | 2.67 ms | 2.74 ms | 沒變 |
| Guest CPU（所有 guest 執行緒合計） | 29.9 ms | 31.1 ms | 各次 29.3／28.7、30.5／33.4，方向不一致，無差異 |
| 遊戲速度、CPU、記憶體 | 1.000、4.86 核、4.9 GB | 1.000、4.84 核、5.0 GB | 沒變 |

**補充：**
- **同一次執行內切換的 A/B：** +1.61 FPS（+1.00..+2.22）、GPU 執行緒 −0.41 ms、1% low +1.67。
- **計時器的條件：** binding、render、guest CPU 這幾列是開啟計時器時量的；計時器會讓兩邊都掉到約 64 FPS，所以只用來分配時間，不代表 FPS。
- **作廢的數據：** 第一次合併 A/B 量到 +5.9 FPS，但它的 off 那一邊比任何一次 legacy 都慢，之後重測沒有重現，不採用。

## D. 撤回的實驗

patch 都封存在 `botw/experiments/`。

| 實驗 | 假設 | 正確性 | 實測 | 原因 |
|---|---|---|---|---|
| Buffer sync memo | 同一個 GPU sequence 內，重複同步同一段 buffer 是空操作，可以跳過 | 第一版有錯，修正後 0 不一致 | +0.13 FPS（不顯著） | 跳過的工作，經過 page table 之後本來就很便宜 |
| Render 執行緒先自旋 50 µs 再睡 | 減少 GPU 執行緒叫醒 render 執行緒時的 kernel 呼叫 | 只改排程，不影響語意 | −0.47 FPS（不顯著） | Profile 裡看起來很大的成本，是取樣器暫停執行緒造成的假象 |
| 命令緩衝 prefetch | 解碼迴圈有三分之一卡在讀命令字（cache miss） | 只是提示，不影響語意 | −0.03 FPS | 沒效果 |

## G. 120 FPS 可行性

| 項目 | 數值 |
|---|---|
| 目前幀時間（optimized） | 11.2–11.6 ms（86–89 FPS） |
| 目標 | 8.33 ms，還差約 3 ms |
| GPU 執行緒延遲傳導到幀時間 | 63%（原本 77%） |
| Render 執行緒餘裕 | 約 1.3 ms |
| 要靠 GPU 執行緒追到 120 | 需要再省約 4 ms，大約是現在的一半 |
| 剩下的候選 | Shader 查詢免比對、頂點格式快取、位址翻譯快取，各 0.1–0.3 ms，加起來不到 1 ms |
| 最大的未解成本 | DLSS 模式額外的約 1.5 ms（只在開 DLSS 時） |
| 之後的瓶頸 | Guest 端：readback 之後的遊戲程式（JIT） |

**120 FPS 沒有達成。** 在不跳過同步、不讀舊資料的前提下，這個場景需要更大的結構改變。可能的方向有兩個：
- guest JIT 本身變快
- 換掉 Ryujinx 的記憶體追蹤模型

這兩個都超出前端重寫的範圍。
